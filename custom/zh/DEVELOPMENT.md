# Zulip 二次开发：开发规范

本仓库是基于 Zulip 13.2 的**二次开发**（自部署 + 定制）。

- 代码：`/home/codyli/zulip`（WSL2 Ubuntu 24.04）
- 分支：`custom/13.x`（从标签 `13.2` 开出，所有定制都在这里）
- 远程：`origin` = `ErduBis/zulip`（我们的 fork），`upstream` = `zulip/zulip`（官方）

## 环境

```bash
cd ~/zulip && source .venv/bin/activate   # 所有 ./tools/ 和 ./manage.py 命令都需要
```

- **开发服务器**：`./tools/run-dev`，访问 `http://localhost:9991`，登录页
  `http://localhost:9991/devlogin/`（无需密码，点测试用户即可）。
  它通常已经在用户的终端里运行，**不要再启动第二个**。先检查：
  `curl -s -o /dev/null -w '%{http_code}\n' http://localhost:9991/devlogin/`
- **测试与检查**（大多要几分钟，放后台跑）：
  - 后端：`./tools/test-backend zerver.tests.test_<模块>`（只跑相关模块，不跑全套）
  - 前端：`./tools/test-js-with-node`（全套也很快，可跟具体文件）
  - lint：`./tools/lint <改动的文件> </dev/null`（含 mypy、TypeScript、prettier）。
    末尾的 `</dev/null` 不能省：其中的提交信息检查在没有终端时会一直等待输入。
    它只检查 git 已跟踪的文件：新建的文件按测试指南「Lint 和类型检查」单独检查，并在汇报里列出。
- **搜索代码**用 `git grep`。
- **sudo**：需要装系统软件或改系统配置时，停下来交给总领。`sudo apt-get`、`sudo apt` 不需要密码，
  其他 sudo 命令由用户输入密码。
- 提示 provision 过期时运行 `./tools/provision`，不要用 `--skip-provision-check` 绕过。

## 角色与路径归属

多个会话**共用这一个目录**，一个路径只归一个角色改。

| 角色           | 负责                                         | 可修改的路径                                                                                                                                          |
| -------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |

| **交互设计**   | 交互流程、界面状态、文案、可用性、设计验收   | `custom/zh/design/`、`custom/en/design/`                                                                                                              |
| **后端**       | 数据模型、业务逻辑、REST API、权限、实时事件 | `zerver/`（不含 `zerver/webhooks/`、`zerver/lib/integrations.py`）、`zproject/`、`analytics/`、`corporate/`、`confirmation/`、`api_docs/`、`zcustom/` |
| **前端**       | Web 界面、交互、样式、模板                   | `web/`、`templates/`（不含 `templates/zerver/integrations/`）                                                                                         |
| **环境与运维** | 开发环境、依赖、部署、备份                   | `tools/`、`scripts/`、`puppet/`、`.github/`，依赖文件 `pyproject.toml`、`uv.lock`、`package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`            |
| **集成与品牌** | 机器人与 webhook 集成、中文翻译、品牌素材    | `zerver/webhooks/`、`zerver/lib/integrations.py`、`templates/zerver/integrations/`、`locale/zh_Hans/`、`static/images/`                               |

各角色自己的测试跟着代码走：后端写 `zerver/tests/`，前端写 `web/tests/`。
需要新增依赖时向总领提出，由环境与运维修改依赖文件。
任何角色都可以在 `web/e2e-tests/` 下创建以 `_claude_` 开头的临时测试文件（`/visual-test` 用），
这些文件已在本地忽略，不会被提交。未列出的路径要改时，先问总领。

### 交互设计

交互设计只写设计方案、不改代码。每个有界面的功能写一份方案，中英两版同名：
`custom/zh/design/<feature-name>.md` 和 `custom/en/design/<feature-name>.md`。方案包括：

1. **目标**：解决谁在什么场景下的什么问题。
2. **入口与流程**：用户从哪里进入，每一步做什么、看到什么。
3. **界面与状态**：每个界面的布局和元素；正常、空、加载中、出错、无权限、内容过长时分别怎样。
4. **文案**：每处界面文字的英文原文和中文译文（Zulip 界面以英文为源文本，中文走翻译文件）。
5. **参照**：沿用 Zulip 里哪些现有组件和交互，保持一致。
6. **适配**：宽屏和手机宽度、浅色和深色主题、键盘操作。
7. **待定问题**：需要用户拍板的取舍，列出选项和各自的代价。

可以附截图标注或 HTML 原型，放在 `custom/zh/design/` 里同名的子目录中。
方案经用户确认后，前端才开始实现。实现完成后，交互设计截图查看实际界面（见「界面检查」），
按方案逐项验收，把偏差列给总领。

## 工作方式

每个任务都按 **理解 → 方案 → 实现 → 验证** 来做。

1. **理解**：读要改的代码和自己角色的指南（见「文档」），用 `git grep` 找代码库里类似的实现照着做。
   说不清「为什么这样改是对的」之前不要动手。
2. **方案**：需求、接口或数据模型没定清楚时，先把理解和打算怎么改讲清楚，确认后再写。
3. **实现**：见下面的「代码要求」。
4. **验证**：相关测试和 lint 必须通过；界面改动要截图看过实际效果（见「界面检查」）。
   想一想可能坏在哪里、怎么证明没坏。

**修 bug**：先复现并确认原因，再修；补一个能抓住这个 bug 的测试；
查一下别处有没有同样的问题。

### 遇到这些情况，先停下来问总领

- 涉及安全（认证、权限、用户输入进 SQL 或 HTML）
- 需要数据库 migration
- 一个改动要同时动多个子系统
- 性能影响说不清
- 需求、接口或数据模型没定清楚
- 现有测试莫名其妙失败
- 要清空开发数据库（`./tools/rebuild-dev-database`、`./manage.py populate_db`）
- 设计或交互上需要取舍——把限制和选项摆出来，不要自己拍板，
  也不要擅自删除、隐藏现有功能或改变交互方式

## 代码要求

- **和周围代码保持一致**，照着现有写法来。
- **命名清晰、方便 `git grep`**：函数、参数、变量、测试名都要能看出用途。
- **不要重复代码**，尤其是权限检查和容易出错的逻辑。
- **注释写「为什么」**，不复述代码在做什么；注释独占一行；密度和附近代码相当。
  不要在注释里描述「这次改了什么 / 修了什么 bug」，那属于提交信息。
  不要在注释里写行号，写函数名。
- **不留**调试代码、注释掉的代码、临时 TODO。
- 用户能看到的文字要**标记翻译**；错误提示要说清楚问题和怎么办。
- 不硬编码密钥或凭证。界面改动注意 **XSS**，服务端改动检查**访问权限**。
- Python：类型注解完整，`Any` 要注释理由；不用字符串拼 SQL；避免 N+1 查询。
- 前端：用 `const`/`let`；用事件委托，不用 `onclick` 属性；用 class/ID 选择器。

### 测试

- 改了什么就测什么，新代码要有测试覆盖。检查自己改的文件有没有漏测：后端用
  `/fix-backend-coverage`，前端用 `/debug-node-coverage`。用 `/fix-backend-coverage` 时去掉命令里的
  `--skip-provision-check`；它提到要改 `tools/test-backend` 时，交给总领安排。
- 测重要的行为，不测内部实现；不仅断言「成功」，还要断言状态确实更新了。
- 错误分支也要覆盖。测试必须能离线跑（外部服务用 fixture）。
- 参考 `zerver/tests/test_example.py`。

### 界面检查

**怎么看界面**：

- 只看不改数据：用 `/screenshot-dev` 登录 `localhost:9991` 截图，再用 Read 查看。
  中文界面加 `--lang zh-hans`，深色主题加 `--dark`。
- 要在页面上点按钮、发消息、改设置来验证：用 `/visual-test`。它在独立的测试服务器（9981 端口）
  和测试数据库上运行，不影响用户的开发数据。`./tools/test-js-with-puppeteer`、`./tools/test-api`、
  `./tools/test-help-documentation` 也用这台测试服务器。**同一时间只能有一个会话使用它**，
  开始前先问总领。

前端交付前自查、交互设计验收时都按这份清单：

- 和相邻、同类元素一致（对齐、间距、字体、颜色）
- 各种状态都正常：悬停、选中、禁用、空、内容过长
- 浅色和深色主题（改了颜色时）
- 宽屏、笔记本、手机宽度
- **中文界面**：中文字体正常，中英文混排时不截断、不错位
- 有权限和没权限的用户各看一次（涉及权限时）
- 没有意外影响别的页面（`git grep` 你改的 CSS 选择器）

## 中文翻译

Zulip 界面以英文为源文本，中文译文放在 `locale/zh_Hans/`：前端文字在 `translations.json`，
后端文字在 `LC_MESSAGES/django.po`。

1. **前端、后端**：界面文字用英文写，并标记为可翻译。不改 `locale/`。
2. **集成与品牌**：运行 `./manage.py makemessages -l zh_Hans` 把新文字加进中文翻译文件，
   填好中文译文（以交互方案里的文案为准），再运行 `./manage.py compilemessages`。
   只用 `-l zh_Hans`，这样不会改动其他语言的文件。
3. **总领**：合并上游时核对 `locale/zh_Hans/`，确保我们加的译文还在；合并后重新运行第 2 步的
   两个命令，再截图检查中文界面。

## 文档

我们自己的文档都放在 `custom/` 下，每份都有中英两版：`custom/zh/` 和 `custom/en/` 里同名、
内容一致。**以中文版为准**；改了一版，同一次改动里同步另一版。
我们自己写的 skill 放在 `.claude/skills/<名称>/`：`SKILL.md` 为中文（会被加载），
同目录的 `SKILL.en.md` 为英文版。

| 文档                | 内容                                                |
| ------------------- | --------------------------------------------------- |
| `DEVELOPMENT.md`    | 开发规范（本文件）                                  |
| `DECISIONS.md`      | 架构与流程决策记录                                  |
| `CUSTOMIZATIONS.md` | 为定制功能对 Zulip 原有代码的修改（升级时逐条核对） |
| `design/`           | 交互设计方案                                        |
| `guides/`           | 分角色的 Zulip 开发指南（见下表）                   |

每个角色动手前先读自己的指南：

| 指南                     | 读者                   | 内容                                                       |
| ------------------------ | ---------------------- | ---------------------------------------------------------- |

## 协作规则

1. **只改自己的路径。** 需要别的角色配合（例如前端需要一个新接口），停下来向总领说明需要什么，
   不要越界去改。
2. **只有总领做 git 写操作。** 执行会话不得 `commit`、`switch`/`checkout`、`stash`、`reset`、
   `rebase`、`push`，也不得 `git add`（暂存区是共用的）。只读命令（`status`、`diff`、`log`、
   `grep`、`show`）随意用。
3. **数据库 migration 只由后端会话生成**，而且生成前先向总领确认数据模型设计。
4. **跨层功能由总领拆分**，按这个顺序推进：
   交互设计出方案并经用户确认 → 总领定接口约定（URL、参数、返回、事件格式）→ 后端实现 →
   前端按方案实现 → 交互设计验收。没有界面的功能跳过设计这两步。
5. **界面以交互方案为准。** 前端遇到方案没覆盖的情况，停下来问，不要自己发挥。
6. **尽量少改 Zulip 原有文件。** 优先用配置、新增文件、新增函数来实现；必须改原有文件时，
   改动保持集中、最小，不顺手重构或格式化无关代码——以后每次升级 Zulip 都要把这些改动重新叠上去。
7. **新增或修改 API 接口**：在 `zerver/openapi/zulip.yaml` 里写好文档（Zulip 的测试会强制检查），
   不改 `API_FEATURE_LEVEL`。

## 完成任务时的汇报格式

做完后向总领汇报（总领据此审查和提交）：

1. **改了哪些文件**：新增 / 修改分开列。
2. **动了哪些 Zulip 原有文件**：逐个说明改了什么、为什么不能不改。
3. **验证**：跑了哪些测试和 lint，结果如何；界面改动怎么看过的。
4. **没做完的、拿不准的、有风险的**。

交互设计汇报：出方案时给出方案文件路径和待定问题；验收时逐项列出实现与方案的偏差。

## 总领的职责

- 把需求拆成任务，指定角色和路径范围，写清验收标准。
- 审查执行会话的改动，提交到 `custom/13.x` 并推送。
- 把每处对 Zulip 原有文件的修改登记到 `CUSTOMIZATIONS.md`。
- 把重要决策记录到 `DECISIONS.md`。
- 定期同步上游：13.x 小版本随时合并；大版本升级单独规划。合并时按「中文翻译」第 3 步核对译文；
  上游改了我们已删除的文件，保持删除（`git rm`）。部署步骤见 `guides/deployment.md`。

### 提交规范

- **一个提交只做一件事**，完整且能独立通过测试；测试和代码放在同一个提交里。
- 移动或拆分文件，和修改内容分成两个提交。
- 不要用后一个提交去修前一个提交的错误，直接改原提交（见 `/git-rebase`）。
- 提交信息中英双语（决策 D10）：标题用 `/commit-message` 的英文格式 `子系统: 概述.`；
  正文先中文（第一段是标题的中文版）、后英文，写 diff 里看不出来的东西。
